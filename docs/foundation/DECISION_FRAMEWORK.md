# 📖 문서 목적

이 문서는 HYB Opportunity AI에서 발생하는 모든 중요한 의사결정에 일관된 기준을 제공하기 위해 작성되었습니다.

기능 추가, 아키텍처 변경, 리팩터링, 기술 도입 등 프로젝트의 방향에 영향을 주는 모든 결정은 이 문서를 기준으로 판단합니다.

---

# 의사결정 원칙

HYB는 감이나 직관보다 명확한 기준을 우선합니다.

중요한 결정은 가능한 한 같은 기준으로 반복 가능하게 이루어져야 합니다.

---

# 최우선 원칙

모든 의사결정은 다음 우선순위를 따릅니다.

1. 정확성
2. 안정성
3. 유지보수성
4. 확장성
5. 사용자 가치
6. 가독성
7. 성능
8. 개발 속도

상위 항목을 희생하면서 하위 항목을 선택하지 않습니다.

예를 들어 성능 향상을 위해 유지보수성이 크게 떨어진다면 해당 선택은 다시 검토합니다.

---

# 기능 추가 판단

새로운 기능은 다음 질문을 모두 통과해야 합니다.

□ 사용자에게 실제 도움이 되는가?

□ 프로젝트의 비전에 맞는가?

□ 유지보수가 가능한가?

□ 테스트가 가능한가?

□ 문서화가 가능한가?

□ 기존 구조를 크게 해치지 않는가?

하나라도 "아니오"라면 개발 전에 다시 검토합니다.

---

# 리팩터링 판단

리팩터링은 다음 목적 중 하나 이상을 만족해야 합니다.

- 코드가 더 이해하기 쉬워진다.
- 테스트가 쉬워진다.
- 중복이 줄어든다.
- 유지보수성이 높아진다.
- 확장성이 좋아진다.

단순히 "더 예뻐 보인다"는 이유만으로는 리팩터링하지 않습니다.

---

# 새로운 기술 도입

새로운 라이브러리나 프레임워크를 도입하기 전에 확인합니다.

□ 정말 필요한가?

□ 기존 기술로 해결할 수 없는가?

□ 장기적으로 유지 가능한가?

□ 프로젝트 복잡도를 증가시키지 않는가?

□ 커뮤니티와 문서가 충분한가?

필요성과 유지보수성을 충분히 검토한 뒤 도입합니다.

---

# AI 제안 평가

AI의 제안은 다음 기준으로 검토합니다.

- 프로젝트 철학과 일치하는가?
- 기존 구조와 충돌하지 않는가?
- 실제로 프로젝트 품질이 향상되는가?
- 장기적으로 도움이 되는가?

AI의 제안은 참고 자료이며, 최종 결정은 Product Owner가 내립니다.

---

# 일정과 품질이 충돌할 때

HYB는 다음 원칙을 따릅니다.

품질을 유지할 수 없는 일정이라면,

일정을 조정합니다.

품질을 희생하여 일정을 맞추는 선택은 가능한 한 하지 않습니다.

---

# 버그 대응

버그가 발생하면 다음 순서로 대응합니다.

1. 원인 확인
2. 영향 범위 분석
3. 수정
4. 테스트 추가
5. 문서 업데이트
6. DEV_LOG 기록

버그 수정은 문제 해결에서 끝나지 않습니다.

같은 문제가 반복되지 않도록 하는 것이 목표입니다.

---

# 문서 변경

문서는 다음 경우 반드시 함께 수정합니다.

- 기능 추가
- 기능 제거
- 구조 변경
- API 변경
- 정책 변경

문서와 코드의 불일치를 최소화합니다.

---

# 충돌하는 선택지가 있을 때

두 가지 선택이 모두 좋아 보인다면 다음 질문을 합니다.

1. 1년 뒤에도 좋은 선택인가?
2. 새로운 개발자가 이해하기 쉬운가?
3. 테스트하기 쉬운가?
4. 프로젝트 철학과 일치하는가?
5. 사용자에게 더 큰 가치를 제공하는가?

이 질문에 더 많이 "예"라고 답할 수 있는 선택을 우선합니다.

---

# 의사결정 기록

중요한 결정은 반드시 기록합니다.

다음 내용이 포함되어야 합니다.

- 결정 내용
- 결정 이유
- 고려했던 대안
- 기대 효과
- 잠재적인 위험

필요한 경우 ADR(Architecture Decision Record) 문서를 작성합니다.
